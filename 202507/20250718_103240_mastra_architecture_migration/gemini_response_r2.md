## 1. Mastraの実装詳細について

### 1-1: Mastraのワークフロー定義と管理

#### 1. ワークフロー定義の方法

**推奨:** **YAML/JSONとTypeScriptのハイブリッドアプローチ**

- **YAML/JSON (構造定義):** ワークフローの全体的な流れ、ステップの順序、並列処理の分岐/結合などを定義します。これにより、ビジネスロジックとオーケストレーションを分離でき、非開発者でもフローの概要を理解しやすくなります。
    ```yaml
    name: ExpenseProcessingWorkflow
    trigger: onFileUploaded
    steps:
      - id: validateFile
        task: 'file-validator' # TypeScriptで実装されたタスクを指す
        input: '$.trigger.fileUri'
        next: parseCsv
      - id: parseCsv
        task: 'csv-parser'
        # ...
    ```
- **TypeScript (タスク実装):** 各ステップ（タスク）の具体的な処理をTypeScriptの関数やクラスとして実装します。これにより、静的型付けの恩恵を受け、複雑なビジネスロジックも安全に記述できます。
- **ビジュアルエディタ:** 初期段階では不要です。まずは定義ファイルベースで確立し、将来的に必要性が高まれば、定義ファイルを自動生成・可視化する内製ツールとして開発するのが現実的です。

**落とし穴:**
- すべてをTypeScriptコードで定義すると、ロジックとフローが密結合し、変更が困難になる可能性があります。
- すべてをJSON/YAMLで表現しようとすると、条件分岐などが複雑になりすぎ、可読性が低下します。

#### 2. エラーハンドリングとリトライ

- **自動リトライ:** 各ステップの定義にリトライポリシーを含めるべきです。
    ```yaml
    - id: sendNotification
      task: 'email-sender'
      retry:
        attempts: 3
        strategy: 'exponential_backoff' # 指数関数的バックオフ
        maxDelay: '60s'
    ```
- **Dead Letter Queue (DLQ):** リトライがすべて失敗したタスクは、メッセージキュー（AWS SQSなど）のDLQに送られます。これにより、失敗したジョブの情報を失うことなく、後から手動での再実行や調査が可能です。
- **部分的再実行:** ワークフローの状態を永続化（DBやRedisなど）しておくことが前提です。失敗したステップから再実行できるように、各ステップは**冪等（べきとう）**に設計することが極めて重要です。例えば、「ファイル処理」ではなく「S3の`file-X.csv`を処理」のように、何度実行しても同じ結果になるようにします。

#### 3. 実行監視とデバッグ

- **ダッシュボード:** [OpenTelemetry](https://opentelemetry.io/) を導入し、トレース情報を収集することを強く推奨します。これにより、各ワークフローの実行状況、ステップごとの所要時間などを可視化できます。JaegerやGrafana Tempoが可視化ツールとして一般的です。
- **ログ:** 構造化ロギング（JSON形式など）を徹底し、すべてのログにワークフローインスタンスIDとステップIDを含めます。これにより、特定のジョブに関連するログの検索が容易になります。
- **ボトルネック特定:** OpenTelemetryで収集したトレースデータにより、どのステップが律速段階になっているかが一目瞭然になります。

### 1-2: 具体的な実装パターン（経費精査フロー）

**推奨アーキテクチャ:** **状態（State）は持たず、参照（Reference）を渡す**

ワークフローエンジン自体は、ファイルの中身のような大きなデータを扱わず、S3のURIなどの参照情報だけをステップ間で受け渡します。実際の処理は、その参照を元に各ワーカー（タスクランナー）が行います。

```typescript
// 1. ファイルアップロード受付 (API Gateway + Lambda/ECS)
//    - この時点でユニークなジョブIDを発行し、S3にファイルを保存。
//    - Mastraワークフローを開始させ、{ jobId, fileUri } を渡す。

// Mastra Workflow
// Step 2: ファイル検証 (Task: file-validator)
//   - fileUriを元にS3からストリームでヘッダー部分のみ読み込み、形式・エンコーディングを検証。

// Step 3: CSVパース (Task: csv-parser)
//   - 大容量ファイル対応のため、S3から直接ストリームで読み込み、1行ずつ処理。
//   - パース結果は、小さなデータ（例: ヘッダー情報、行数）なら次のステップに渡す。
//   - 大量の中間データは、別のS3オブジェクトやDBに保存し、その参照を渡す。

// Step 4: ビジネスルール適用 (並列処理)
//   - Workflow EngineがFan-outパターンで並列処理を開始。
//   - 例えば、CSVを1000行ずつのチャンクに分割した情報（オフセットとリミット）を各ワーカーに渡す。
//   - 各ワーカーは担当範囲の行をS3からストリームで読み込み、並列でルールを適用。

// Step 5: 結果ファイル生成 (Fan-inパターン)
//   - 並列処理ワーカーからの結果（例: 各チャンクの結果が保存されたS3 URIリスト）を集約。
//   - 結果をマージして最終的な結果ファイルを生成し、S3に保存。

// Step 6-8: S3保存、通知、履歴更新
//   - これらは独立したタスクとして順次実行。
//   - DB更新と通知のような外部連携では、トランザクション境界が課題になる。
//     -> **Transactional Outboxパターン** を検討。DBへの書き込みと「通知イベント」の書き込みを同一トランザクションで行い、別のプロセスがイベントを読み取って実際に通知を送信する。
```

## 2. 移行戦略の具体化

### 2-1: API Gateway層の実装

#### 1. API Gatewayの選択肢

- **AWS API Gateway:** AWSエコシステムに深く依存している場合に最適。IAMとの統合、マネージドサービスである点が強み。
- **Kong:** オープンソースで拡張性が高い。オンプレミスやマルチクラウド環境で強力。プラグインで機能を柔軟に追加可能。
- **Nginx Plus:** パフォーマンス重視。ただし、API管理機能は上記2つに比べて限定的。

**推奨:** **AWS API Gateway** から始めるのが最も手軽で、多くのユースケースをカバーできます。認証（Cognito Authorizer）やルーティング（パスベース、ヘッダーベース）も容易に設定可能です。

#### 2. Rails-Mastra間の通信

- **プロトコル:** **REST** で始めるのが無難です。デバッグが容易で、既存のツールや知識を活かせます。サービス間通信のパフォーマンスが明確なボトルネックになった時点で gRPC への移行を検討します。
- **サービス間認証:** **IAM Role**（AWS内通信の場合）や、**JWT** を用いたクライアント認証が一般的です。API GatewayでJWTを検証し、バックエンドサービスには検証済みのユーザー情報などをヘッダーで渡すのがクリーンな設計です。
- **データ一貫性:** 最終的な結果整合性（Eventual Consistency）を許容する設計が基本です。厳密な一貫性が必要な場合は、前述のSagaパターンやTransactional Outboxパターンを導入します。

### 2-2: データ移行とスキーマ管理

#### 1. データベース移行

- **ベストプラクティス:**
    1. `prisma introspect` で既存DBからスキーマ定義を生成。
    2. ActiveRecordのコールバック（`before_save`など）やスコープ、モデル内のビジネスロジックを、Mastra側のサービスクラスやリポジトリ層に明示的に再実装する。**この自動化は困難であり、最も注意が必要な作業です。**
- **二重書き込み戦略:**
    - Strangler Figパターンと並行して行います。
    - Rails側で書き込みが発生した際に、同期的にMastraのAPIを呼ぶか、非同期にイベント（SQSなど）を発行してMastra側でデータを取り込みます。非同期を推奨します。
- **整合性検証:** 定期的にバッチ処理を動かし、両方のDBのレコードを比較・検証するスクリプトが必要です。

#### 2. 既存データの扱い

- **ジョブ履歴:** ビジネス要件次第です。古い履歴の参照頻度が低いなら、Rails側に残したままにし、参照リクエストだけRailsに流すのが現実的です。
- **S3上の既存ファイル:** **移動させる必要はありません。** Mastra側から同じS3バケットにアクセスできるようIAMロールを設定すれば十分です。パスの互換性は、Mastra側で古いパス形式を解釈できるようにアダプターを設けることで対応します。

## 3. パフォーマンスとスケーラビリティ

### 3-1: 具体的なパフォーマンス要件

これは貴社のビジネス状況によりますが、以下を考慮してMastraのワーカーを設計します。

- **Node.jsでの最適化:**
    - **Worker Threads:** CPUバウンドな処理（複雑な計算、小規模なファイルのインメモリでのパースなど）に有効です。ただし、I/Oバウンドな処理（S3からのストリーミングなど）では効果が薄いです。
    - **Cluster Mode:** 主にWebサーバー（API受付層）で、マルチコアを活かしてネットワークリクエストを捌くために使います。ワークフローのワーカーとしては、コンテナオーケストレーションによる水平スケーリングの方が一般的です。
    - **メモリ管理:** **ストリーム処理の徹底**が最も重要です。巨大なファイルをメモリに一括で読み込むコードは絶対に避けてください。

### 3-2: インフラ構成

- **Kubernetes (K8s) 構成:**
    - **APIサーバー (Deployment):** HTTPリクエストを受け付け、ワークフローを開始させる。CPU使用率に基づくHPA（Horizontal Pod Autoscaler）。
    - **ワークフローエンジン (Deployment):** 状態管理とタスクのスケジューリングを行う。
    - **ワーカー (Deployment or KEDA):** 実際のタスクを実行する。タスクキュー（SQSなど）のメッセージ数に基づいてスケーリングさせるのが最も効率的です。[KEDA (Kubernetes Event-driven Autoscaling)](https://keda.sh/) はこのための優れたツールです。
- **監視とアラート:**
    - **Prometheus + Grafana:** コンテナリソース（CPU/メモリ）、キューの長さ、タスク処理時間などのメトリクスを収集・可視化。
    - **OpenTelemetry:** アプリケーションレベルのトレースとメトリクスを収集。
    - **SLI/SLO:** 「ファイルのアップロード完了から結果通知までの時間の中央値が5分未満」「ジョブ成功率99.9%」のように、ユーザー体験に基づいた目標を定義し、アラートを設定します。

## 4. セキュリティとコンプライアンス

### 4-1: セキュリティ要件

- **データ保護:**
    - **転送時:** すべての通信でTLS 1.2以上を強制。
    - **保存時:** S3のサーバーサイド暗号化（SSE-S3またはSSE-KMS）を有効化。DBも暗号化。
    - **PII:** ワークフローの早い段階でPIIを検知・マスキングするステップを入れることを検討。
- **認証・認可:**
    - **OAuth2/OIDC:** [Auth0](https://auth0.com/)や[AWS Cognito](https://aws.amazon.com/cognito/)のようなマネージドサービスを利用することを強く推奨します。自前実装は非常に困難で危険です。
    - **マルチテナント:** JWTのカスタムクレームに`tenant_id`を含め、API Gatewayやバックエンドでテナント分離を強制します。

### 4-2: 監査とコンプライアンス

- **監査ログ:** 「いつ、誰が、どのリソースに、何をしたか」を記録します。特に、ファイルのアップロード、削除、設定変更などの重要な操作はすべてログに残します。
- **ログの改ざん防止:** AWS CloudWatch Logsや、書き込み専用のS3バケットにログを出力し、アクセス権を厳格に管理します。
- **規制対応:** 設計段階から、データの流れ、アクセス制御、暗号化、ログ記録の方針をドキュメント化しておくことが、将来の認証取得を容易にします。

## 5. 開発チームへの影響

### 5-1: スキルセット移行

- **教育計画:**
    - **RailsとNode/TSの概念マッピング:** 「ActiveRecordモデル vs Prismaスキーマ+サービスクラス」「Gem vs npmパッケージ」のような対比ドキュメントを作成。
    - **段階的投入:** まずは小規模なAPIや、副作用の少ない読み取り専用のワークフロータスクの実装から始めてもらう。
    - **ペアプログラミング:** TypeScript経験者とRails開発者がペアで作業する時間を設けるのが最も効果的です。
- **開発プロセス:**
    - **CI/CD:** ESLint/Prettierによる静的解析、Jest/Vitestによる単体・結合テスト、Dockerイメージのビルドと脆弱性スキャン、K8sへのデプロイ、というパイプラインを構築します。

### 5-2: 移行期間中の生産性

- **並行開発の課題:**
    - **明確な所有権:** ある機能が「Rails担当」なのか「Mastra担当」なのかを明確に定義し、ドキュメント化します。
    - **API契約:** API Gatewayを介したサービス間通信では、OpenAPI (Swagger) などでAPI仕様を厳密に定義し、契約ベースで開発を進めます。
    - **バグ修正:** 移行期間中は、両方のシステムで同じバグを修正する必要が出てくる可能性があります。これは移行のコストとして受け入れ、修正箇所と影響範囲をチームで密に共有することが重要です。
