## 経費監査機能 要件定義ヒアリングガイド (最終版)

このガイドは、経費監査機能の要件定義を成功させるための、ファシリテーション手法、補足ツール、リスク管理、そしてネクストアクションを網羅した実践的な手引書です。Why→What→Howのフレームワークを軸に、質の高い要件定義を実現しましょう。

### 1. 効果的なヒアリング進行のためのファシリテーションガイド

#### 1.1. アイスブレイクと場作り (最初の5分)
- **目的とゴールを明確に共有:**「本日は『経費監査プロセスの非効率を解消し、ガバナンスを強化する』という目的のため、皆様から具体的な要件をお伺いします。最終的には、全員が納得できるシステム要件定義書を作成することを目指します。」
- **アジェンダの確認:** 時間配分を含めてアジェンダを提示し、参加者からの合意を得ます。「本日は、Why(背景・目的)に30分、What(監査要件)に60分、How(システム化)に30分という流れで進めさせていただきます。」
- **心理的安全性の確保:**「完璧な答えは必要ありません。現時点での課題感やアイデアを自由にお話しください。特に『現場の非効率』といった生々しい情報は大歓迎です。」

#### 1.2. 議論が脱線した時の軌道修正方法
- **「駐車場 (Parking Lot)」の活用:** ホワイトボードや付箋に「駐車場」エリアを作成します。「非常に重要なご意見ありがとうございます。本筋から少し外れるため、一旦『駐車場』に置かせていただき、後ほど必ず議論する時間を設けます。」
- **アジェンダへの立ち返り:**「〇〇様、ありがとうございます。その点は△△の議論で重要になりますね。アジェンダに沿って、まずは□□のテーマから進めさせていただけますでしょうか。」
- **目的の再確認:**「私たちの目的は『経費監査の自動化』でした。今のお話は、その目的達成にどのように繋がりますでしょうか？」

#### 1.3. 時間管理のコツ
- **タイムキーパーの任命:** 参加者の中からタイムキーパー役を依頼するか、ファシリテーターが兼務します。
- **時間区切りの宣言:**「では、これからの15分間で『不正検知のパターン』についてアイデアを出し尽くしましょう。」
- **残り時間の可視化:**「このテーマの残り時間はあと5分です。最も重要なポイントをまとめに入りましょう。」

#### 1.4. 合意形成のテクニック
- **要点のサマリーと確認:**「ここまでの議論をまとめると、『領収書の目視確認は、5万円以上の交際費に限定する』ということで皆様よろしいでしょうか？」
- **反対意見の尊重と深掘り:**「なるほど、その点には懸念がおありなのですね。具体的にどのような問題が考えられますか？」
- **暫定合意と次回への申し送り:**「本日は『A案を第一候補とする』という形で暫定合意とし、各部署で影響範囲を調査いただいた上で、次週最終決定するという進め方はいかがでしょうか。」

### 2. 要件定義の品質を高める補足ツール

#### 2.1. 要件の曖昧さチェックリスト (5W1H)
ヒアリング中に、以下の点が不明確な場合は即座に確認します。

- **Who (誰が):** その操作はどの部門の、どの権限を持つ人が実行できますか？承認者は？
- **When (いつ):** 月次？申請時？リアルタイム？締め日の何日前まで？
- **Where (どこで):** PC？スマホアプリ？どの画面でその情報は表示されますか？
- **What (何を):** 対象となる経費は？（例: 全ての交際費？特定の勘定科目のみ？）
- **Why (なぜ):** なぜそのチェックが必要ですか？（法的要件？社内規程？不正防止？）
- **How (どのように):** 具体的な手順は？エラー時はどうなりますか？例外処理は？
- **How Much/Many (どのくらい):** 上限金額は？チェックする件数は？

#### 2.2. ヒアリング中に使える可視化ツール（テンプレート）
複雑な要件は、その場で図に描いて認識を合わせます。

- **業務フロー図:** 誰が何をして、情報がどう流れるかを可視化する。
  `[申請者] → (申請) → [一次承認者] → (承認/差戻し) → [経理担当] → (監査) → ...`
- **状態遷移図:** １つの経費申請がどのようなステータスを辿るかを示す。
  `[下書き] ⇄ [申請中] ⇄ [差戻し] → [承認済] → [監査NG] → [支払済]`

### 3. リスク回避のためのチェックポイント

#### 3.1. よくある要件定義の失敗パターン
- [ ] **目的の形骸化:** 「なぜ」が忘れられ、機能追加そのものが目的になっていないか？
- [ ] **ステークホルダーの欠落:** 経理、営業、監査役など、関係者全員が参加しているか？
- [ ] **現状維持バイアス:** 「今のやり方」に固執し、本質的な改善を妨げていないか？
- [ ] **例外処理の沼:** 発生頻度の低い例外ケースの議論に時間を使いすぎていないか？（80%の主要ケースをまず固める）

#### 3.2. 経費監査システム特有の落とし穴
- [ ] **法令・規程の解釈違い:** 電子帳簿保存法、インボイス制度、社内規程の理解は全員一致しているか？
- [ ] **マスターデータの不備:** 正しい従業員データ、組織データ、勘定科目マスターはどこから取得できるか？
- [ ] **監査ルールの陳腐化:** 将来のルール変更に備え、設定変更のしやすさ（柔軟性）は考慮されているか？
- [ ] **監査担当者のUX軽視:** 監査画面が見にくい、操作が煩雑だと、結局監査品質が低下しないか？

#### 3.3. プロジェクト後半で問題になりやすい点
- [ ] **非機能要件の欠落:** パフォーマンス（大量データ処理速度）、セキュリティ（アクセス権限）は考慮されているか？
- [ ] **データ移行の計画:** 過去の経費データを新システムにどう取り込むか？
- [ ] **導入・教育コストの軽視:** 新しいシステムを全社に展開するための計画とコストは見積もられているか？

### 4. ヒアリング後のネクストアクション

#### 4.1. 要件定義書への落とし込み方
1. **議事録の清書と共有:** ヒアリング後、24時間以内に議事録を共有し、認識齟齬がないか確認する。
2. **要件の構造化:** ヒアリング内容を以下の構成で要件定義書にまとめる。
    - **1. 背景と目的 (Why):** プロジェクトの存在意義
    - **2. スコープ:** 対象範囲（やること）と対象外範囲（やらないこと）
    - **3. 機能要件 (What):** ユーザーの役割別に、何ができるかを記述（ユーザーストーリー形式が有効）
    - **4. 非機能要件 (How):** パフォーマンス、セキュリティ、可用性など
    - **5. 制約事項:** 法令、技術的制約、予算、納期など

#### 4.2. ステークホルダーへの確認プロセス
1. **ドラフトレビュー:** まずはコアメンバーで要件定義書のドラフトをレビューし、完成度を高める。
2. **公式レビュー会:** 全ステークホルダーを招集し、レビュー会を実施。変更・修正点を洗い出す。
3. **最終承認 (サインオフ):** 修正版を最終確認してもらい、正式な承認を得る。これにより、後の「言った言わない」問題を防ぐ。

#### 4.3. プロトタイプ作成の優先順位
全ての要件を一度に作るのではなく、価値が高く、不確実性も高い領域からプロトタイプを作成し、手戻りを防ぎます。

- **最優先:** **監査担当者向けのチェック画面。** 最も複雑で、業務効率に直結するため、早期にUI/UXを確認すべき。
- **優先度:高:** **監査ルールの設定画面。** ルール変更の柔軟性を担保できるか、技術的な実現可能性を探る。
- **優先度:中:** **管理者向けのダッシュボード。** 全体の傾向を把握する画面。コア機能が固まった後でも良い。
- **優先度:低:** **単純な申請・承認フロー。** 既存機能の流用や、仕様が明確な部分は後回し。
