## 経費監査システム 要件定義 - 統合質問票・ヒアリングガイド

このドキュメントは、経費監査システムの要件定義（Phase2）を具体化するための質問票、ヒアリングの進め方、および次のステップを定義するものです。

### 1. 統合質問票

ヒアリングを効率的に進めるため、質問をカテゴリに分け、優先度（Must/Should/Nice to Have）を明記しました。

#### **カテゴリA：全体方針とビジネス目標**
（対象ステークホルダー：事業責任者、経理部長、プロジェクトマネージャー）

*   **A-1 [Must Have]** このシステム導入によって達成したい、最も重要なビジネス目標は何ですか？（例：不正検知率の向上、監査工数の削減、ガバナンス強化）
*   **A-2 [Must Have]** システムの導入対象となる範囲（部署、子会社など）はどこですか？ 将来的に拡大する予定はありますか？
*   **A-3 [Should Have]** プロジェクトの予算と、Phase2で目指すリリース時期の目安を教えてください。

#### **カテゴリB：監査ロジックとビジネスルール**
（対象ステークホルダー：経理部長、監査担当者、経費精算業務担当者）

*   **B-1 [Must Have]** 現在、どのような基準で経費を監査していますか？（例：金額、勘定科目、業者、添付書類の有無）既存のルールブックやチェックリストがあればご共有ください。
*   **B-2 [Must Have]** 監査で検知すべき項目を、重要度（高・中・低）で分類してください。（例：高：私的利用、中：交際費の上限超過、低：勘定科目の間違い）
*   **B-3 [Must Have]** 監査ルールに違反した場合、どのようなレベル（警告、エラー、要承認など）で、誰に通知・アクションを求めますか？
*   **B-4 [Should Have]** 監査ルールはどの程度の頻度で、誰が変更・追加する必要がありますか？（例：年に1回開発者が、月に1回経理担当者が）
*   **B-5 [Should Have]** 将来的に、機械学習（ML）を用いて不正・異常パターンを自動で検知するような高度な監査機能に興味はありますか？
*   **B-6 [Nice to Have]** 役職や部署によって、適用する監査ルールを変える必要はありますか？

#### **カテゴリC：ユーザーインターフェースと体験（UI/UX）**
（対象ステークホルダー：監査担当者、経費申請者、承認者）

*   **C-1 [Must Have]** 監査担当者が最もよく使う機能は何ですか？ 監査結果の確認・修正画面で、どのような情報を一覧で確認したいですか？
*   **C-2 [Must Have]** 監査でNGとなった場合、申請者にはどのようなメッセージが表示されるべきですか？ 修正を促すための分かりやすいガイダンスは必要ですか？
*   **C-3 [Should Have]** 監査状況（未処理、処理中、完了など）の進捗が分かるダッシュボードは必要ですか？
*   **C-4 [Nice to Have]** スマートフォンやタブレットからも監査業務を行えるようにする必要はありますか？

#### **カテゴリD：システム連携と拡張性**
（対象ステークホルダー：IT部門、開発リード）

*   **D-1 [Must Have]** このシステムは、どのシステムと連携する必要がありますか？（例：TOKIUMインボイス、TOKIUM経費精算、会計システム、人事マスタ）
*   **D-2 [Must Have]** データ連携の方式と頻度はどうしますか？（例：APIでリアルタイム、日次バッチでCSV連携）
*   **D-3 [Should Have]** 将来的に、外部システムがこの監査システムの結果を利用するためのAPI（Webhookなど）を提供する必要はありますか？
*   **D-4 [Nice to Have]** プラグインのような形で、個別企業向けのカスタム監査ロジックを追加できるようなアーキテクチャを検討しますか？

#### **カテゴリE：非機能要件**
（対象ステークホルダー：IT部門、事業責任者）

*   **E-1 [Must Have]** ピーク時に処理すべき経費申請の件数はどのくらいですか？ 監査処理の応答時間はどの程度を期待しますか？（例：95%の処理が5秒以内に完了）
*   **E-2 [Must Have]** どのようなセキュリティ要件がありますか？（例：アクセスログの取得、IPアドレス制限、SSO連携）
*   **E-3 [Must Have]** 監査証跡として、どのような操作ログを、どのくらいの期間保存する必要がありますか？（電子帳簿保存法への対応など）
*   **E-4 [Should Have]** システムの目標可用性（稼働率）はどのくらいですか？（例：99.5%） 障害発生時の目標復旧時間（RTO）は？

#### **カテゴリF：レポーティングと分析**
（対象ステークホルダー：経理部長、経営層、監査担当者）

*   **F-1 [Must Have]** 監査結果に関する定型レポートとして、どのようなものが必要ですか？（例：月次の監査結果サマリー、違反項目ランキング）
*   **F-2 [Should Have]** 監査データを多角的に分析するための、インタラクティブなダッシュボードは必要ですか？（例：部署別、費目別の違反傾向分析）
*   **F-3 [Nice to Have]** レポートの出力形式（PDF, Excel, CSV）は何をサポートすべきですか？

### 2. 想定される回答の影響分析

主要な質問に対する回答が、システム設計に与える影響を分析します。

| 主要な質問 | 回答の選択肢 | 設計への影響 |
| :--- | :--- | :--- |
| **B-4: 監査ルールの変更頻度と担当者** | A) 頻度は低く、開発者が対応 | ・監査ロジックはコード内に実装可能。<br>・開発コストは低いが、変更の柔軟性も低い。 |
| | B) 頻度は高く、経理担当者が対応 | ・**ルールエンジン**の導入が必須。<br>・経理担当者向けのルール設定画面が必要。<br>・初期開発コストは高いが、運用効率と柔軟性が向上する。 |
| **D-1: TOKIUMとの連携** | A) 経費精算データのみ連携 | ・TOKIUM経費精算のAPI仕様に準拠した連携モジュールを開発。 |
| | B) インボイスや他のデータも連携 | ・複数のTOKIUM製品APIに対応する必要があり、連携の複雑性が増す。<br>・データモデルの設計がより重要になる。 |
| **E-2: セキュリティ要件（認証）** | A) ID/パスワード認証 | ・基本的な認証機能を実装。 |
| | B) SSO（SAML/OIDC）連携 | ・IdP（Identity Provider）との連携設計が必要。<br>・セキュリティは向上するが、開発・テストの工数が増加する。 |
| **(参考) マルチテナント対応の要否** | A) 不要（自社利用のみ） | ・シングルテナントアーキテクチャで設計。<br>・データモデル、インフラ共にシンプル。 |
| | B) 必要（グループ会社や顧客に提供） | ・**アーキテクチャの根幹に関わる最重要決定事項。**<br>・データベース設計（スキーマ分離 or Tenant ID）、カスタマイズ機能、インフラ構成など全てに影響。初期段階での決断が不可欠。 |

### 3. ヒアリングの進め方の推奨事項

1.  **推奨される質問順序:**
    *   **Step 1: 全体像の確認 (カテゴリA)** - まずビジネス目標とスコープを明確にし、関係者全員の目線を合わせます。
    *   **Step 2: コア機能の深掘り (カテゴリB, C)** - 最も重要な監査ロジックと、それを実際に使う画面の要件を詰めます。
    *   **Step 3: 技術・周辺要件の確認 (カテゴリD, E, F)** - システム連携や非機能要件など、技術的な制約と拡張性を定義します。

2.  **確認すべきステークホルダー:**
    *   **ビジネス要件（A, F）:** 事業責任者、経営層、経理部長
    *   **業務要件（B, C）:** 経理部長、監査担当者、一般の経費申請者・承認者
    *   **技術要件（D, E）:** IT部門責任者、インフラ担当、開発リード

3.  **事前に準備してもらうべき情報:**
    *   既存の経費規定、監査ルール、チェックリスト
    *   監査で問題となった経費申請の具体例（個人情報等はマスク）
    *   連携対象システムの概要と、可能であればAPI仕様書
    *   月間・年間の平均的な経費申請件数

### 4. 要件定義の次のステップ：要件定義書の構成案

ヒアリングで得た回答を基に、以下の構成で要件定義書を作成します。

#### **経費監査システム 要件定義書 - 構成案**

1.  **はじめに**
    1.1. 背景と目的（質問A-1の回答を基に記載）
    1.2. システムのスコープ（対象範囲、対象外範囲）（A-2）
    1.3. 用語の定義

2.  **システム概要**
    2.1. ビジネスプロセスフロー（As-Is / To-Be）
    2.2. システム構成図（連携システムを含む）

3.  **機能要件**
    3.1. 監査機能（カテゴリBの回答を詳細化）
        - 3.1.1. 監査ルール一覧
        - 3.1.2. 監査実行プロセス
        - 3.1.3. 監査結果通知
    3.2. ユーザーインターフェース要件（カテゴリC）
        - 3.2.1. 監査ダッシュボード
        - 3.2.2. 監査結果詳細画面
    3.3. レポーティング機能（カテゴリF）
        - 3.3.1. 定型レポート一覧
        - 3.3.2. 分析ダッシュボード
    3.4. 管理者機能
        - 3.4.1. ユーザー管理
        - 3.4.2. （必要であれば）監査ルール管理

4.  **非機能要件**
    4.1. 性能・拡張性（E-1）
    4.2. 可用性・信頼性（E-4）
    4.3. セキュリティ（E-2）
    4.4. 法令・コンプライアンス（監査証跡、個人情報保護など）（E-3）

5.  **外部インターフェース要件**
    5.1. TOKIUM連携（D-1, D-2）
    5.2. 会計システム連携
    5.3. （必要であれば）外部公開API（D-3）

6.  **その他**
    6.1. 移行要件（旧システムからのデータ移行など）
    6.2. 開発・テスト・デプロイメントに関する制約
