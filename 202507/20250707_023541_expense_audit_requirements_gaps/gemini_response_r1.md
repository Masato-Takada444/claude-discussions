### 1. 現状の要件ドラフトに不足している主要な要件

ご提示のチェックリストに基づき、現在のドラフトに不足している、あるいは具体性が欠けている主要な要件を以下のように特定しました。

*   **非機能要件:** パフォーマンス目標、セキュリティの詳細（データ暗号化、アクセス制御）、可用性の目標（SLA）、ログの要件などが全く定義されていません。
*   **運用要件:** エラー発生時の具体的な復旧手順、ユーザーへの通知方法、監査ログやアップロードされたファイルの具体的な保存期間とアーカイブ戦略、管理者向けの機能（エラー調査、データ参照など）が不明確です。
*   **ビジネスルール詳細:** 複数の監査ルールに抵触した場合の優先順位や、ルールの例外条件（例：特定の条件下では許可されるタクシー利用）、判定結果の粒度（単なるOK/NGだけでなく、警告レベルの有無など）、将来的なルール追加・変更への柔軟性が考慮されていません。
*   **ユーザビリティ:** エラー発生時のメッセージ内容、大容量データ処理中の進捗表示、ユーザーが正しいCSVを用意するためのガイド（テンプレート提供など）、監査結果のサマリー表示といった、利用者の体験を高める要件が不足しています。
*   **法規制・コンプライアンス:** 経費データに含まれる個人情報の取り扱い方針、内部統制や外部監査に耐えうる証跡としての要件、法的に定められたデータ保存期間などが考慮されていません。

### 2. 不足要件を明確化するための質問票

上記の不足要件を具体化し、関係者との合意形成を円滑にするための質問票を以下に作成しました。

### 経費監査システム Phase2 要件定義・質問票

#### 1. 非機能要件
システムの品質と安定稼働を担保するために定義します。

| 質問 | この質問の意図 | 優先度 |
| :--- | :--- | :--- |
| **1.1 パフォーマンス** | | |
| 1.1.1 一度の監査で処理するCSVファイルの最大行数やファイルサイズはどの程度を想定していますか？（例: 1万行、10MB） | サーバーのスペックや、処理を同期的（即時）に行うか非同期的（バックグラウンド）に行うかのアーキテクチャ選定に必須の情報です。 | **必須** |
| 1.1.2 監査開始から結果通知までの許容時間はどのくらいですか？（例: 5分以内） | ユーザー体験に直結します。時間がかかる場合、進捗表示や完了通知の仕組みが重要になります。 | **重要** |
| **1.2 セキュリティ** | | |
| 1.2.1 アップロードされたCSVファイルや監査結果は、サーバー上で暗号化して保存する必要がありますか？ | 個人情報や経費情報という機密情報を保護するために不可欠な要件です。 | **必須** |
| 1.2.2 過去の監査結果を閲覧できるユーザーに制限はありますか？（例: 実行者本人のみ、特定の管理者のみ） | 不正なアクセスを防ぎ、誰がどのデータにアクセスできるかを明確にするためのアクセス制御の設計に必要です。 | **必須** |
| **1.3 可用性** | | |
| 1.3.1 このシステムの目標稼働率はどのくらいですか？（例: 99.5%）また、計画メンテナンスは許容されますか？ | どの程度の信頼性が求められるかを定義し、インフラ構成（冗長化など）を決定するために必要です。 | **重要** |
| 1.3.2 システム障害時、どのくらいの時間で復旧させる必要がありますか？また、最大でどのくらいのデータ損失が許容されますか？ | RTO（目標復旧時間）とRPO（目標復旧時点）を定義し、バックアップ・リストア戦略を策定するために必要です。 | **重要** |
| **1.4 保守性・監視** | | |
| 1.4.1 どのようなログ（操作ログ、エラーログ等）を、どのくらいの期間保存する必要がありますか？ | 障害発生時の原因調査や、不正操作の追跡、利用状況の分析に不可欠です。 | **重要** |

#### 2. 運用要件
システムを安定して運用し続けるために定義します。

| 質問 | この質問の意図 | 優先度 |
| :--- | :--- | :--- |
| **2.1 エラー処理とリカバリー** | | |
| 2.1.1 監査処理中に予期せぬエラーで中断した場合、ユーザーは再実行する必要がありますか？システムが自動でリトライしますか？ | ユーザーの負担を軽減し、システムの信頼性を高めるためのエラーハンドリング方針を決定します。 | **必須** |
| 2.1.2 メール送信に失敗した場合、どうなりますか？（例: 時間を置いて再送、管理者に通知） | 結果通知の信頼性を担保するための重要な仕様です。 | **必須** |
| **2.2 データ管理** | | |
| 2.2.1 監査ログやアップロードされたCSVファイルは、法規制や社内規定に基づき、最低何年間保存する必要がありますか？ | ストレージコストや、コンプライアンス要件を満たすためのデータ保持ポリシーを策定するために必要です。 | **必須** |
| 2.2.2 保存期間を過ぎたデータは、自動的に削除またはアーカイブ（長期保管用の別領域へ移動）しますか？ | データ管理の運用負荷とコストを最適化するためのライフサイクル管理方針を決定します。 | **重要** |
| **2.3 管理者機能** | | |
| 2.3.1 システム管理者は、ユーザーの監査実行履歴やエラー内容を確認する画面が必要ですか？ | ユーザーからの問い合わせ対応や、障害調査を効率的に行うための運用機能の要否を判断します。 | **重要** |
| 2.3.2 特定の監査を、管理者が代理で再実行する機能は必要ですか？ | ユーザーが解決できない問題を運用でカバーするためのリカバリー手段として検討します。 | **推奨** |

#### 3. ビジネスルール詳細
監査ロジックの精度と柔軟性を高めるために定義します。

| 質問 | この質問の意図 | 優先度 |
| :--- | :--- | :--- |
| 3.1 1つの経費明細が複数の監査ルール（例: 「アルコール検知」と「人跨ぎ重複」）に抵触した場合、結果に両方表示しますか？それとも優先度の高いルールのみ表示しますか？ | 監査結果の表示方法を明確にし、ユーザーが混乱しないようにするためのルールです。 | **必須** |
| 3.2 監査結果を「エラー（許容されない）」、「警告（注意喚起）」、「情報（参考）」のようにレベル分けする必要はありますか？ | 監査結果の重要度をユーザーに伝え、対応の優先順位付けを助けるための仕様です。 | **重要** |
| 3.3 将来的に監査ルール（例: タクシー代の上限金額）を、エンジニアの手を借りずに管理者が変更できる機能は必要ですか？ | ビジネスの変化に迅速に対応するための、システムの柔軟性と拡張性を決定する重要な要素です。 | **重要** |
| 3.4 監査ルールの例外条件はありますか？（例: 「役員の場合はタクシー代の上限を緩和する」など） | 監査の精度を高め、誤検知を減らすために、ビジネスの実態に合わせた例外処理を定義します。 | **推奨** |

#### 4. ユーザビリティ
利用者が迷わず快適に使えるようにするために定義します。

| 質問 | この質問の意図 | 優先度 |
| :--- | :--- | :--- |
| 4.1 CSVのフォーマットが違うなど、入力データに不備があった場合、どのようなエラーメッセージを表示しますか？（例: 「CSVのヘッダーが不正です。正しいフォーマットは...」） | ユーザーが自力で問題を解決できるように、具体的で分かりやすいフィードバックを提供するためです。 | **必須** |
| 4.2 監査対象のデータ量が多い場合、処理中であることがわかるような進捗表示（プログレスバーなど）は必要ですか？ | ユーザーに「処理が止まっているのでは？」という不安を与えず、安心して待てるようにするためです。 | **重要** |
| 4.3 ユーザーが正しいフォーマットのCSVを用意できるよう、テンプレートCSVファイルをダウンロードできる機能は必要ですか？ | ユーザーの操作ミスを減らし、サポートへの問い合わせを削減する効果が期待できます。 | **推奨** |
| 4.4 メールでの結果送付だけでなく、画面上でも「監査が完了し、5件の違反が検知されました」のようなサマリーを表示する必要はありますか？ | 監査結果の概要を即座に把握できるようにし、ユーザー体験を向上させるためです。 | **推奨** |

#### 5. 法規制・コンプライアンス
法的リスクを回避し、企業の信頼性を担保するために定義します。

| 質問 | この質問の意図 | 優先度 |
| :--- | :--- | :--- |
| 5.1 経費データに含まれる氏名などの個人情報の取り扱いについて、社内のプライバシーポリシーや法規制（個人情報保護法など）上の要件はありますか？ | 法令遵守を確実にするための設計（例: データマスキング、アクセスログの取得）に反映させるためです。 | **必須** |
| 5.2 このシステムの監査証跡（誰が、いつ、どのデータで監査し、結果がどうだったか）は、内部統制や外部監査の要件を満たす必要がありますか？ | 監査証跡の信頼性・完全性を担保するための要件（例: ログの改ざん防止）を定義します。 | **必須** |

---

この質問票を活用し、ビジネス部門や運用部門の関係者とディスカッションすることで、より具体的で網羅的な要件定義が可能となり、手戻りの少ないスムーズな開発へと繋がります。
