## 経費監査機能 要件定義 - 詳細ヒアリング項目

### 1. 実装の詳細に関する質問

#### **監査ルールの柔軟性**

| 質問 | この質問が重要な理由 | 質問しない場合のリスク |
| :--- | :--- | :--- |
| **Q1: 複数の監査ルールを組み合わせた条件（AND/OR）を設定できますか？**<br>例：「役職が部長以上」**かつ**「金額が5万円以上」の場合にアラートを出す。 | 実際の監査は単純なルールだけでなく、複数の要素を組み合わせて判断することが多いため。 | ルールが単純化されすぎ、本当に注意すべき申請を見逃したり、逆に不要なアラートが多発して監査効率が低下する。 |
| **Q2: ルールに対する例外条件（特定の部署や個人を除くなど）を定義できますか？**<br>例：「全社員のタクシー代は1万円まで」だが、「役員は例外とする」。 | 業務の特性上、例外的な処理は必ず発生するため。柔軟な制度運用にシステムが対応できるかを確認する必要がある。 | 例外規定のたびに手動での確認・承認が必要になり、システム化の恩恵が薄れる。現場の不満にもつながる。 |
| **Q3: 複数のルールに抵触した場合、表示される警告の優先順位を設定できますか？** | 申請者や承認者にとって、どの違反が最も重要かを直感的に理解させ、修正を促しやすくするため。 | 重要度が低い警告が先に表示され、クリティカルな問題が見過ごされる可能性がある。ユーザーが混乱し、確認の手間が増える。 |
| **Q4: 金額の閾値やキーワードなどのルール設定値を、管理者（経理担当者など）が画面上で簡単に変更できますか？** | 会社の規定変更や暫定的な運用ルール変更に、エンジニアの手を借りずに迅速に対応できるようにするため。 | ルール変更のたびに開発部門への依頼が必要になり、時間とコストがかかる。ビジネスの変化に迅速に対応できない。 |

#### **エッジケースの処理**

| 質問 | この質問が重要な理由 | 質問しない場合のリスク |
| :--- | :--- | :--- |
| **Q5: 監査で一度否認・差戻しされた申請が修正・再申請された場合、監査はどのように行われますか？**<br>（全体を再監査するのか、変更点のみを監査するのか） | 再申請時のワークフローを明確にしないと、監査漏れや二重チェックが発生する可能性があるため。 | 修正によって新たに発生した問題を検知できなかったり、逆に不要な再監査に時間を費やしたりする。 |
| **Q6: 新しい監査ルールを追加した場合、過去に承認済みのデータに遡って適用（遡及監査）する必要はありますか？** | 内部統制やコンプライアンスの観点から、過去の申請も新しい基準でチェックする必要があるかを事前に確認するため。 | 将来、遡及監査が必要になった際に、対応する機能がなく手作業での膨大な確認作業が発生する。 |
| **Q7: 1つの申請書に複数の経費明細が含まれる場合、監査は明細単位で行いますか？申請単位（合計金額など）で行いますか？** | 監査の粒度を定義するため。例えば「1明細5千円未満はOK」でも「合計で10万円を超えたらNG」といったルールを考慮する必要がある。 | 「チリツモ」での高額申請を見逃したり、逆に個々の明細は問題ないのに合計金額で不必要に警告が出たりする。 |

#### **運用面の詳細**

| 質問 | この質問が重要な理由 | 質問しない場合のリスク |
| :--- | :--- | :--- |
| **Q8: 監査ルールの変更は、誰が、どのような承認プロセスを経て行いますか？変更履歴は管理されますか？** | 監査ルールの正当性と一貫性を担保し、不正なルール変更を防ぐため。ガバナンスの観点で非常に重要。 | 誰がいつルールを変更したか追跡できず、監査の信頼性が揺らぐ。内部統制上の問題点として指摘される可能性がある。 |
| **Q9: 期末や年末年始など、特定の期間だけ適用する一時的なルール（またはルールの緩和/強化）を設定できますか？** | 季節や時期によって経費の使い方が変動する実態に、システムを合わせるため。 | 繁忙期に不要なアラートが多発して業務が滞ったり、逆に通常期に特別な支出が見逃されたりする。 |
| **Q10: 組織変更（部署の統廃合、異動など）があった場合、人に紐づく監査ルールは自動で更新されますか？** | 人事情報と連携していない場合、組織変更のたびに手動での大規模なメンテナンスが必要になるため。 | 異動前の部署のルールが適用され続けたり、新しい役職のルールが適用されなかったりして、監査が正しく機能しなくなる。 |

### 2. 見逃しがちな観点

| 質問 | この質問が重要な理由 | 質問しない場合のリスク |
| :--- | :--- | :--- |
| **Q11: (AI/機械学習) 個人の過去の申請パターンと比較して異常な点を検知するような、AIによる自動異常検知は必要ですか？** | 明確なルール違反ではないが「いつもと違う」という、人間の目では見つけにくい不正やミスの兆候を捉えるため。 |巧妙な不正（少額の不正を繰り返すなど）や、ルール化しにくい非効率な経費利用を見逃し続けることになる。 |
| **Q12: (監査の効率性) 全件監査ではなく、リスクの高い申請に絞ったり、一定の割合で抜き打ちチェックしたりするサンプリング監査の機能は必要ですか？** | 監査担当者の負担を軽減し、限られたリソースをより重要な監査に集中させるため。 | 全ての申請に同じ労力をかけることになり、監査業務が非効率になる。結果として、重要な問題を見落とすリスクが高まる。 |
| **Q13: (監査証跡) 「なぜこの判断が下されたのか」という監査の根拠（どのルールに抵触したか、誰が承認したか）を、申請ごとに明確に記録・表示できますか？** | 監査の透明性と説明責任を確保するため。後から問い合わせがあった場合や、内部・外部監査の際に必須となる。 | 監査判断の正当性を証明できず、従業員からの不満や、監査法人からの指摘につながる。 |
| **Q14: (多言語・多通貨) 海外出張などで発生した外貨での支払いは、どの時点の為替レートで円換算して監査しますか？レートの取得元はどこですか？** | 為替レートの変動による意図しないルール違反や、逆に高額な経費の見逃しを防ぐため。換算基準の統一は必須。 | 換算基準が曖昧なため、不公平な監査結果になったり、経理処理時に金額が合わなくなったりする。 |
| **Q15: (モバイル対応) 監査者や承認者は、スマートフォンアプリなどから、領収書の画像を確認し、承認・否認の操作を行えますか？** | 承認プロセスが滞るボトルネックを解消するため。場所を選ばずに作業ができれば、経費精算全体のスピードが向上する。 | 承認者が自席のPCでしか作業できず、出張中などに承認が滞留する。結果として、従業員への支払い遅延などが発生する。 |

### 3. 段階的な導入を想定した質問

| 質問 | この質問が重要な理由 | 質問しない場合のリスク |
| :--- | :--- | :--- |
| **Q16: (MVP) 最初のリリース（MVP）で絶対に外せない、最も基本的で重要な監査機能・ルールは何ですか？**<br>（例：交際費の上限チェック、事前申請との突合など） | 投資対効果を最大化し、早期に価値を提供するため。全ての機能を最初から作ろうとすると、開発が長期化し、失敗リスクが高まる。 | 機能が過剰になり、開発期間とコストが膨れ上がる。本当に必要な機能がいつまでもリリースされない「塩漬け」状態になる。 |
| **Q17: (拡張性) 将来的に、人事システムや会計システム、法人カードのデータなど、他のシステムと連携する可能性はありますか？** | 手動でのデータ入力を減らし、監査の自動化レベルを上げるため。将来の拡張を見据えた設計（APIなど）が必要か判断する。 | 将来システム連携が必要になった際に、大規模な改修が必要になる。連携を前提としない設計は、拡張性の低い「閉じられた」システムになる。 |
| **Q18: (パイロット運用) もし試験的に導入する場合、どの部署を対象にするのが最も効果的ですか？また、その運用で何を検証したいですか？**<br>（例：営業部で「使いやすさ」を、経理部で「監査精度」を検証するなど） | 本格導入後の手戻りをなくすため。限定的な範囲で利用してもらい、課題を洗い出すことで、全社展開のリスクを低減できる。 | 全社展開していきなり問題が多発し、大規模な混乱を招く。ユーザーからの信頼を失い、システムの利用が定着しなくなる。 |
