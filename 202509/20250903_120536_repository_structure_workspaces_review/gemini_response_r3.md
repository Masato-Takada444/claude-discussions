## 3. リスク軽減策の具体化

### 質問3.1: 最も重要なリスク軽減策TOP3

1.  **Dockerビルドコンテキストの最適化（.dockerignore）**
    - **理由：** これを怠ると、不要なファイル（ルートの`node_modules`など）がDockerイメージに含まれ、ビルド時間が激増し、セキュリティリスクも生じます。モノレポ化で最も陥りやすい罠の一つです。
2.  **ESM/CommonJSの統一方針決定**
    - **理由：** `backend`(CJS)と`frontend`(ESM)でモジュール形式が異なるため、`shared-types`の扱いが問題になりがちです。最初は**「全パッケージをCommonJSで出力する」**と決めてしまうのが最もトラブルが少ないです。
3.  **CI/CDでのdepcheck導入**
    - **理由：** Workspaces構造では、依存関係がどの`package.json`に書かれるべきか混乱しがちです。「未使用の依存」や「`package.json`に記載漏れの依存」を機械的に検知する仕組みは、健全性を保つ上で非常に重要です。

### 質問3.2: 「やってはいけない」アンチパターンTOP3

1.  **ワークスペース間の循環参照**
    - 例：`backend`が`frontend`に依存するような構造。これはビルドや依存関係解決を不可能にします。依存関係は必ず一方向に（例：`backend` -> `shared`, `frontend` -> `shared`）。
2.  **個別のパッケージにしか使わない依存をルートに置く**
    - 例：`express`をルートの`package.json`に`dependencies`として追加してしまう。これはWorkspacesの利点である関心事の分離を破壊し、依存関係を不透明にします。
3.  **`npm install`を各ワークスペースで個別に実行する**
    - 必ず**ルートディレクトリで`npm install`を一度だけ**実行します。個別に実行すると依存関係の解決が壊れ、`node_modules`が複数できてしまい、問題の温床となります。

## 4. 移行シナリオの詳細

### 質問4.1: もし将来pnpmに移行する場合

提示された手順でほぼ完璧です。1点だけ、最も重要な注意点を追加します。

**追加すべきステップ/注意点：**
- **Step 3.5: 依存関係の厳密化**
  - `pnpm install`を実行した後、**「幽霊依存（Phantom Dependencies）」**が原因でアプリケーションが失敗する可能性があります。npm/yarnでは暗黙的に利用できていたパッケージが、pnpmでは明示的な`dependency`追加を要求されることがあります。
  - これはpnpmの利点（厳密性）ですが、移行時にはエラーとして現れるため、`package.json`への依存関係の追加作業が必要になる可能性があります。

### 質問4.2: Next.js導入時の構造変更

事前に決めておくべき方針は以下の通りです。

1.  **frontendの置き換え**: その通りです。`frontend`ディレクトリを`create-next-app`で置き換えます。
2.  **APIルートの配置**: **独立した`backend`を維持することを推奨します。**
    - **理由：** Next.jsのAPI Routesはステートレスな処理やBFF（Backend for Frontend）に適していますが、現在の`backend`は独立したAPIサーバーとしての役割を持っています。これを維持することで、関心事の分離が保たれ、将来的に管理画面以外のクライアント（例：モバイルアプリ）が登場した場合も対応が容易です。
3.  **環境変数の管理**: Next.jsは`NEXT_PUBLIC_`プレフィックスでクライアント側に公開する環境変数を管理します。現在の`.env`分離構成はそのまま活かせますが、Next.jsの規約に従う必要があります。
4.  **ビルド・デプロイ戦略**:
    - `npm run build`は、Next.jsアプリのビルドと`backend`のビルドを両方実行するようにルートの`package.json`で設定します。
    - デプロイは2つのユニット（Next.jsアプリ、backendサーバー）を別々にデプロイする戦略になります（例：Next.jsはVercelへ、backendはDockerコンテナとしてCloud Run/ECSへ）。

## 5. 具体的な実装例の確認

### 質問5.1: npm-run-allの設定

はい、その設定で**`Ctrl+C`ですべてのプロセスが正しく終了します。** `npm-run-all`はSIGINTシグナルをすべての子プロセスに伝播させるように設計されています。

エラー時の挙動もデフォルトで適切です。いずれかのプロセスがエラーで終了した場合、他のプロセスは実行を続けます。もし1つが失敗したら全てを停止させたい場合は、`--race`オプションを追加します。

### 質問5.2: 環境変数の扱い

**はい、dotenv-cliなしで管理可能です。**

多くのNode.jsフレームワーク（HonoのNode.jsサーバーアダプタも含む）は、内部で`dotenv`ライブラリを標準的に使用しています。プロセスが起動したディレクトリにある`.env`ファイルを自動で読み込みます。

したがって、`npm run dev --workspace=backend` を実行すると、`backend`ディレクトリでプロセスが起動し、`backend/.env`が自動的に読み込まれます。この構成で問題ありません。

## 7. 実装後のサポート

### 質問7.1: よくあるトラブルと解決策TOP3

1.  **問題：`shared-types`パッケージの変更が`backend`/`frontend`に反映されない。**
    - **原因：** `shared-types`のビルド（JSへのコンパイル）が実行されていない。
    - **解決策：** `shared-types`に`"dev": "tsc -w"`のようなwatchモードのスクリプトを追加し、`npm-run-all`で`backend`, `frontend`と同時に起動する。
2.  **問題：`backend`や`frontend`から`shared-types`を`import`できない（`Module not found`）。**
    - **原因：** TypeScriptの`paths`設定、または`package.json`の`dependencies`設定が間違っている。
    - **解決策：**
        - 各ワークスペースの`tsconfig.json`で`"paths": { "@app/shared-types": ["../../packages/shared-types/src"] }`のような設定を確認する。
        - `backend`/`frontend`の`package.json`で`"dependencies": { "@app/shared-types": "workspace:*" }`という依存が正しく記述されているか確認する。
3.  **問題：Dockerビルドが非常に遅い、またはローカルと挙動が違う。**
    - **原因：** `.dockerignore`の設定不備により、ホストの`node_modules`や不要なファイルがコンテキストに含まれている。
    - **解決策：** `.dockerignore`を徹底的に見直し、ビルドに必要なファイル（例：`backend/`ディレクトリ、`packages/`ディレクトリ、ルートの`package.json`と`package-lock.json`）のみをコンテキストに含めるようにする。
